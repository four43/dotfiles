# Give Claude a part kit, a validator and eyes

A Claude skill builds good three.js game models when it treats the GLB as **compiled output**. The source is a numeric part spec and a small Node script: three.js geometry helpers produce the parts, and glTF-Transform assembles the node tree, skins and clips. The skill then checks the result in a fixed order: the Khronos validator, semantic checks written in code, a three.js reload with animations sampled, and finally rendered contact sheets that Claude reads as PNGs. The research consistently says code is no longer the hard part. With error feedback, frontier models write executable 3D code more than 97% of the time. What still fails is **spatial correctness**: floating parts, misaligned parts, wrong axes, along with renamed nodes and malformed skins that load silently broken. Vision critique catches some of these and misses others, so the skill should check numbers, names, weights and normals in code, and use images for intent, proportion and readability. Everything needed already runs on this machine without Blender. Playwright's cached headless Chromium renders a labeled 6-view sheet of the tractor in about 0.3 s through SwiftShader. Node can load untextured GLBs with three.js and sample `AnimationMixer` deterministically. The project's `models.mjs`/`tools/glb.mjs` already follow the "three.js geometry → glTF-Transform writer" pattern the evidence favors. The last section turns this into a concrete skill: SKILL.md outline, four bundled scripts, five reference files, a capped loop and an eval set.

## Script the parts, compile with glTF-Transform, keep Blender optional

Almost all academic work on LLM-authored 3D targets Blender Python. LL3M builds assets with planner, coder, critic and verifier agents writing bpy ([LL3M](https://arxiv.org/html/2508.08228v1)). SceneCraft compiles scene-graph constraints into Blender scripts ([SceneCraft](https://arxiv.org/pdf/2403.01248)). 3DCodeBench scores 12 VLMs on Blender code ([3DCodeBench](https://arxiv.org/pdf/2606.01057)). That evidence carries over to this project, but the tooling does not. Blender is not installed. `pip install bpy` is pinned to Python 3.11/3.13 ([PyPI bpy](https://pypi.org/project/bpy/)). BlenderMCP needs a running GUI, and in August 2026 its maintainer's GitHub account was reported compromised ([HN](https://hn.algolia.com/api/v1/items/49238028)). The closest practitioner analogue that needs no Blender is img2threejs: an agent skill that writes procedural three.js `Group` factories with pivots, sockets and colliders, and gates each pass on browser renders ([img2threejs SKILL.md](https://github.com/img2threejs/img2threejs/blob/main/SKILL.md)).

Two routes write the GLB from Node. three.js `GLTFExporter` handles hierarchy, skins and animations in Node after a ten-line `FileReader` shim. It cannot export textures without a canvas, though. It also writes `matrix` instead of TRS unless animations are passed, and it drops invisible children unless `onlyVisible:false` is set ([GLTFExporter r186](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/exporters/GLTFExporter.js)). glTF-Transform has no DOM dependency and takes embedded PNG bytes directly. A hand-assembled skinned, animated document from it passed the Khronos validator with **0 errors and 0 warnings** and played correctly in `AnimationMixer` (verified locally against three 0.186.1 / glTF-Transform 4.5.1). glTF-Transform is too verbose for the model to write vertex buffers in by hand, so the right split is three's `BoxGeometry`/`CylinderGeometry`/`LatheGeometry` for shapes and glTF-Transform for nodes, materials, skins, clips and writing. `models.mjs` already works this way. Blender becomes worth installing only for smooth-skinned organic characters, bevel/modifier-heavy hero props, or baked textures. Text-to-3D APIs (Meshy, Tripo, Rodin) return dense, unnamed, unhierarchied meshes, which defeats the goal of named sockets and pivots ([Meshy MCP](https://cdn.jsdelivr.net/gh/pasie15/meshy-ai-mcp-server@main/README.md)).

| Route | Runs here now | Hierarchy, sockets, skins, clips | Fit |
|---|---|---|---|
| three.js geometry → glTF-Transform document | Yes | Full, explicit TRS, validator-clean | **Default** |
| three.js scene → GLTFExporter (Node shim) | Yes, no textures | Full, but watch `trs`, `onlyVisible`, track names | Fallback for quick rigid props |
| Blender bpy headless | Install needed | Full, plus modifiers, UV unwrap, heat weights | Organic/hero assets only |
| OpenSCAD / CadQuery / CSG | Install needed | Single solids, no hierarchy | Wrong output style |
| Text-to-3D APIs | Network + keys | None semantic | Wrong output style |

## Spatial and naming errors dominate, and code catches them first

3DCodeBench found that multi-turn error feedback lifts executability **from about 70% to over 97%**. The remaining failures are physical: disconnected parts, wrong structural alignment, axis violations ([3DCodeBench summary](https://www.emergentmind.com/papers/2606.01057)). LL3M reports that **about 41% of user edits needed 3–4 rounds** to fix placement, and its VLM critic "occasionally miss[es] disconnected components" ([LL3M](https://arxiv.org/html/2508.08228v1)). VoxelCodeBench attributes **about 40% of failures to hallucinated API attributes**. Its in-context examples helped weak models but cut a strong Claude model by 34.8 points through context dilution ([VoxelCodeBench](https://arxiv.org/html/2604.02580v1)). For the skill, that argues for a short, curated API cheat-sheet and a helper library over pages of examples. Practitioners report the same pattern: relationship-based placement ("left of", "on top of") with numbers solved last, and a render-to-PNG-and-inspect loop ([HN thread](https://hn.nuxt.dev/item/46591100)). spec-3d-model turns "3D spatial reasoning AI is bad at" into code generation by putting a JSON spec of constants and topology first ([spec-3d-model](https://github.com/zhuchaokn/spec-3d-model)).

The glTF-specific failures are worse because most of them load without any error. They are mechanical, and each maps to a check that runs before any image is rendered:

| Silent failure | Cause | Check |
|---|---|---|
| `getObjectByName('Bone.Base')` returns undefined | GLTFLoader sanitizes names: spaces → `_`, `[ ] . : /` removed ([GLTFLoader r186](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/loaders/GLTFLoader.js), [PropertyBinding r186](https://github.com/mrdoob/three.js/blob/r186/src/animation/PropertyBinding.js)) | Names match `^[A-Za-z0-9_]+$` and are unique |
| Sockets vanish after optimizing | `prune()` removes empty leaf nodes by default ([prune](https://gltf-transform.dev/modules/functions/functions/prune)) | Always `prune({keepLeaves:true})`; assert every spec socket exists after reload |
| Skinned mesh offset or ignoring parent | The spec ignores the skinned node's transform ([glTF 2.0 §3.7.3](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html)); the validator warns `NODE_SKINNED_MESH_NON_ROOT` | Skinned mesh at scene root, identity TRS |
| Weight errors | Weights not summing to 1, or lazy `[0,1,0,0]` joint indices | Validator `ACCESSOR_WEIGHTS_NON_NORMALIZED` / `ACCESSOR_JOINTS_USED_ZERO_WEIGHT`, plus a per-vertex sum check |
| Validator crashes | Float32 `JOINTS_0` | Joints stored as `Uint8Array`/`Uint16Array` only |
| Model renders pure black | No `NORMAL` attribute, which still passes the validator with 0 errors (verified locally) | Assert normals are present |
| Faces inside-out | Hand-written winding | Signed volume > 0 and normal/winding agreement, with edges keyed by quantized position, not index |
| 360° spin clip doesn't move | slerp between identical quaternions | At least 3 keys for a full turn, or spin the node in game code |
| `GLTFExporter` throws on clip | Track named `Body.skeleton.bones[x].position` | Name tracks by bone directly (`upper.position`) |
| Model faces backwards or floats | Convention drift | +Y up, front faces +Z, meters, bottom-center origin ([glTF 2.0 §3.4](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html); [3DC guidelines](https://github.com/mlimper/3DC-Asset-Creation/blob/main/asset-creation-guidelines/RealtimeAssetCreationGuidelines.md)) |

Two rigging conclusions follow. First, most game "rigs" in this project don't need a skin. Parenting each rigid part to a node pivoted at its joint and animating `rotation` produces the same motion, and wheels, loader arms, doors, and the chicken's wings and legs fit this pattern. A skin earns its complexity only when one continuous surface must bend. Second, when a skin is needed, rigid per-part weights (`joints=[k,0,0,0]`, `weights=[1,0,0,0]`) are the robust default. A segment blend across the joint band is the next step up. Both are simple enough to generate in code, and neither needs Blender's heat-map weighting ([glTF 2.0 spec](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html); [glTF-Transform Skin](https://gltf-transform.dev/modules/core/classes/Skin)).

## A labeled contact sheet renders in 0.3 seconds on this machine

Headless Chromium is the only renderer here that matches the game. `headless-gl` supports only WebGL1, and three.js removed WebGL1 in r163 ([three.js forum](https://discourse.threejs.org/t/suggestions-for-unit-testing-with-headless-gl-and-webgl-2/66891)). The cached `chromium_headless_shell-1243` rendered `tractor.glb` into a 1152×768 six-view sheet through `ANGLE (Vulkan, SwiftShader)` in **291 ms including browser launch**, with no flags (local experiment). Two fresh pages rendering the same frame at `antialias:false`, `setPixelRatio(1)`, with no rAF loop, produced **0 differing pixels**, so golden-image tests are viable. Two cautions apply. `playwright@1.64` expects browser build 1248, so the scripts must pass `executablePath` to the cached 1243 shell. And `--disable-gpu` silently forces SwiftShader, which matters if anyone later tries GPU rendering ([microlink](https://microlink.io/blog/webgl-without-a-gpu)). The repo's `tools/models.html` already has an importmap for `node_modules/three`. Serving that tree through `page.route` avoids running a dev server.

Layout matters more than resolution. Claude bills images at `ceil(w/28)×ceil(h/28)` tokens and downscales anything over its long-edge limit. Below about 200 px, hallucination rises. Counting and localization are only "approximate" ([Anthropic Vision docs](https://platform.claude.com/docs/en/build-with-claude/vision)). VLMs fail at overlap, intersection and counting when shapes sit close together, and reach near-100% when the shapes are spaced apart ([BlindTest](https://arxiv.org/html/2407.06581v4)). GPTEval3D found that multi-view sheets with normal renders in the same layout, plus view labels, improved judgments ([GPTEval3D](https://arxiv.org/html/2401.04092v2)). The design that follows is one sheet of about 1200×800 px (about 1,230 tokens), with six tiles of at least 384 px: orthographic FRONT/RIGHT/BACK/LEFT/TOP plus a 3/4 perspective. Each view is framed tightly on the model's bbox, with a ground grid sized to the bbox and a 1 m reference cube off the +X/−Z corner where it can't occlude. A text footer carries the bbox in meters, triangle and draw counts, and clip names. The local test showed that a fixed frame left the subject at about 25% of each tile and the cube occluding the tractor, so auto-framing is required. A second sheet carries the diagnostics. A normals pass with `FrontSide` on magenta exposes flipped or missing faces as magenta holes; on the barn this showed up immediately. A clay pass separates shape from color. A helper pass draws `AxesHelper` and a sparse name label on every socket and bone.

Claude reads only the first frame of a GIF, so animation must arrive as stills ([Anthropic Vision docs](https://platform.claude.com/docs/en/build-with-claude/vision)). A filmstrip of 8 samples per loop (or 12 per one-shot) from a fixed side ortho camera, labeled `t=0.25s (2/8)` and closed with a tile pairing t=0 against t=duration, shows whether a walk "reads". Foot sliding, popping, loop seams and joint collapse are numeric questions. VLMs are documented to be weak at cross-view and relative-position reasoning ([MultiView summary](https://arxiv.org/abs/2512.02340v1)), so the same page should compute these from `mixer.setTime()` samples and print them as JSON next to the PNG.

## Critique works as a checklist and fails as "does it look right?"

Render-critique loops help, but only modestly, and they fail toward false acceptance. In CADCodeVerify the VLM writes 2–5 yes/no questions from the spec before looking, then answers them against four views. It beat the show-and-fix baseline by **7.3% point-cloud distance**, yet its answers were only **65–68% accurate** ([CADCodeVerify](https://arxiv.org/html/2410.05340v2)). A 2026 TikZ study measured visual-verifier F1 of at most 0.815. It found that strong models gained mainly from verification that "prevents premature acceptance", and that feedback helps only when it is precise, actionable, complete and grounded in the original instruction ([Reux et al.](https://arxiv.org/abs/2606.15693)). LL3M splits the critic, which lists issues, from a verifier that compares before/after renders against that list to confirm each fix landed ([LL3M](https://arxiv.org/html/2508.08228v1)). GPTEval3D found pairwise "is A better than B on X" judgments track humans better than absolute scores ([GPTEval3D](https://arxiv.org/html/2401.04092v2)).

So the skill should hold Claude to a fixed critique protocol. The binary checks are written from the spec before the image is opened ("front view shows the grille", "rear wheels larger than front", "no magenta holes except the listed barn door"). Each check is answered Yes, No or Unclear with the tile it relies on. An Unclear triggers a zoomed single-view render and never counts as a pass. Every No gets a node-level fix. After an edit, the before and after sheets are shown together as labeled images and each prior No is re-checked. img2threejs supplies the control structure: "scripts enforce, agents judge", state lives in a file and not in context, each review ends in exactly one decision (continue, refine spec, refine code, ask the user, stop), and corrections are capped at **3 per pass and 6 in total** ([img2threejs](https://github.com/img2threejs/img2threejs/blob/main/SKILL.md)). Without the caps the loop polishes forever, and without the file state it forgets what it already fixed after compaction.

## One `node --test` command tests the models and evals test the skill

Model testing splits into four layers, ordered cheapest first, and the first three need no GPU. The first is the Khronos validator: `validateBytes(bytes, {maxIssues:0, writeTimestamp:false, ignoredIssues:['NODE_EMPTY']})` returns coded messages with JSON pointers and an `info` block of triangle, draw-call and max-influence counts ([gltf-validator](https://www.npmjs.com/package/gltf-validator)). Failing on severity ≤ 1 with `assert.deepEqual(bad, [])` hands the agent the exact code and pointer to fix. `NODE_EMPTY` must be allow-listed, because every socket triggers it. The second layer is data checks over glTF-Transform accessors: finite positions, normals present, per-vertex weight sums, at most 4 influences, unit quaternions, strictly increasing keys, grounded bottom-center bbox, height in range, signed volume, boundary and non-manifold edge counts, and power-of-two textures. Each is 5–20 lines, and all of them passed on the project's barrel, cone and bale (verified locally). The third layer is behavioral: `GLTFLoader.parseAsync` in plain Node, after stripping textures to avoid `self is not defined`, then `PropertyBinding.findNode` for every track. Sampling `mixer.setTime(t)` with `skeleton.update()` lets the test assert that sockets stay above ground, that the skinned bbox doesn't collapse, and that loops close, using `SkinnedMesh.getVertexPosition` ([SkinnedMesh docs](https://threejs.org/docs/pages/SkinnedMesh.html)). The fourth layer is opt-in pixel goldens under SwiftShader, compared with pixelmatch or `toHaveScreenshot` ([Playwright](https://playwright.dev/docs/api/class-pageassertions)). It should stay limited to one angle per model and one mid-pose per key clip. Per-asset expectations belong in a manifest modeled on the Khronos 3D Commerce validator's min/max schema ([3dc-validator](https://cdn.jsdelivr.net/npm/@mikefesta/3dc-validator@1.0.0/README.md)), so failures read "wheel_FL missing; found wheel_fl" rather than "assertion failed".

The skill itself needs separate evals. Anthropic's guidance is to run real tasks *without* the skill first, turn the failures into at least three scenarios, and only then write instructions. It also recommends testing with a fresh Claude instance and watching which files it reads or ignores ([Anthropic skill best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)). skill-creator's loop runs with-skill and without-skill subagents per eval, grades scriptable assertions automatically, and leaves subjective quality to a human viewer. For triggering, it optimizes the description on 20 near-miss queries ([Anthropic engineering blog](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)). For a GLB skill nearly every objective assertion can run through the skill's own `inspect`/`validate` scripts. Only "does it look like a tractor" needs a judge, and that judge should be a pairwise comparison against the no-skill baseline.

## Recommended skill: `glb-author`

**Placement and frontmatter.** Put the skill at `~/.claude/skills/glb-author/` so other games can use it, as a sibling to `web-3d-game`. `web-3d-game` covers loading and running models, and `glb-author` covers making them. Each should link to the other in one line. Use `name: glb-author`. The description should be third-person and slightly pushy, and should name the triggers: "Builds low-poly 3D game models as GLB/glTF files for three.js from code: multi-mesh props, node hierarchies, pivots, empty socket/attachment nodes, vertex-color or palette textures, bones/skins and animation clips. Validates, renders multi-view contact sheets and animation filmstrips to check its own work. Use whenever the user asks to make, model, rig, animate, fix or inspect a .glb/.gltf asset or a 3D model for a web game, even if they don't say GLB." Add `allowed-tools: Bash(node *)` to cut permission prompts. Keep SKILL.md under about 250 lines. Anthropic's ceiling is 500, and reference files should sit one level deep ([best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)).

**Layout.**

```text
glb-author/
├── SKILL.md
├── scripts/                     # executed, never read; each prints ≤60 lines + exits non-zero on failure
│   ├── kit.mjs                  # imported by model scripts: part helpers + glTF-Transform writer
│   ├── inspect.mjs              # GLB → compact YAML facts
│   ├── validate.mjs             # GLB (+spec) → pass/fail with named, measured-vs-expected errors
│   ├── look.mjs                 # GLB → contact sheets / filmstrips PNG + facts JSON (Playwright)
│   ├── page.html                # the three.js render page look.mjs drives
│   └── state.mjs                # iteration ledger: next step, caps, decisions
├── references/
│   ├── conventions.md           # axes, units, origin, naming, spec schema
│   ├── hierarchy-sockets.md     # nodes vs meshes vs primitives, pivots, extras→userData, prune gotcha
│   ├── materials-textures.md    # COLOR_0 linear, palette UV trick, sRGB, flipY, no-texture default
│   ├── rigging-skins.md         # rigid-node rigs first; skin rules, IBMs, weights, verified snippet
│   └── animation-clips.md       # channels, quaternions, track names, 360° rule, clip naming
├── templates/
│   ├── prop.model.mjs           # rigid multi-part prop with sockets (e.g. hay wagon)
│   └── critter.model.mjs        # node-rigged animal with walk/idle clips
└── evals/
    ├── evals.json
    └── files/                   # specs + one deliberately broken GLB per failure class
```

**SKILL.md outline.** (1) *Purpose and the one default*: author in a `<name>.model.mjs` that imports `scripts/kit.mjs`, never hand-edit GLB bytes, and treat Blender as the escape hatch for organic skinned characters only. (2) *Conventions block*, inlined because every task needs it: meters, +Y up, front faces +Z, bottom-center origin, names `[A-Za-z0-9_]`, moving parts pivoted at their node origin, sockets as empty nodes `Socket_<Name>` with `extras.socket`. (3) *Copyable checklist*: spec → build → inspect → validate → look → critique → decide, with "only proceed when validate passes". (4) *The spec format* (`<name>.spec.json`): parts with size, parent, attach-to, pivot and color; sockets; bones; clips with duration and loop flag; budgets; expected bbox; plus a `checks` array of the binary visual questions, written before any render. (5) *Script commands* with one-line usage each. (6) *Critique protocol*: images first, then answer each spec check Yes/No/Unclear with the tile cited; Unclear means rerun `look --zoom <node>`; each No gets a node-level fix; after an edit, show before/after and re-check. (7) *Loop rules and caps* (below). (8) *Reference table*: one row per file, saying when to read it. (9) *Hand-off*: copy to `assets/models/`, add the spec to the test manifest, and run `npm test`.

**Bundled scripts.** All are Node ESM using what the project already has: three 0.186, `@gltf-transform/core` + `extensions` 4.5, and `pngjs`. Add `@gltf-transform/functions`, `gltf-validator` and `playwright` (library only, pointed at the cached `~/.cache/ms-playwright/chromium_headless_shell-1243` via `executablePath`), plus `pixelmatch` for goldens.

| Script | What it does | Output Claude sees |
|---|---|---|
| `kit.mjs` | `box/cyl/lathe/wedge(name, dims, {at, rotDeg, color})`, `group(name, pivot)`, `socket(name, at)`, `rigidRig(parts→joints)`, `clip(name, {node: {rotDeg/pos keys}})`, `writeGLB(path)`. It converts sRGB colors to linear COLOR_0, un-welds for flat shading, uses Uint8 joints, keeps skinned meshes at the root, and runs `dedup()` + `prune({keepLeaves:true})` | Thrown errors with the part name |
| `inspect.mjs <glb>` | Tree with type (mesh/empty/bone), TRS in degrees, world bbox, tris per mesh, materials/textures, skins and joint counts, clips with duration, targets and unresolved names | ~30–60 lines of YAML |
| `validate.mjs <glb> [--spec s.json]` | Khronos validator (severity ≤1 fails, `NODE_EMPTY` allowed), then data checks (normals, NaN, weights, quats, keys, grounding, bbox vs spec, signed volume, holes, POT textures, budgets), then three.js reload: every spec name resolves, every track binds, sockets stay above ground and skinned bbox stays stable across 20 samples, loops close | `PASS` or numbered `FAIL [code] node: measured vs expected; did you mean …` |
| `look.mjs <glb> --sheet geo\|diag\|anim [--clip walk] [--zoom node] [--ref img.png] [--before old.png]` | One browser per batch. `geo` = 6 ortho/persp tiles auto-framed with grid, 1 m cube and footer. `diag` = normals-on-magenta, clay, wire, socket/bone axes and labels. `anim` = 8/12-frame filmstrip plus seam tile, with foot-slide, pop, seam and collapse numbers. `--ref`/`--before` compose labeled side-by-sides; with a reference, silhouette IoU per view | PNG path(s) + facts JSON, under 1 s per sheet |
| `state.mjs next\|record` | Reads/writes `<name>.state.json`: pass, attempt counts, last decision, open Nos | The exact next command and remaining budget |

**Workflow loop and caps.** Pass 0 is *spec*: Claude writes the spec and the visual checks, then runs `validate --spec-only` to lint the schema (plan-validate-execute). Pass 1 is *blockout*: correct parts, hierarchy, names, sockets and bbox, with no color. Gate: `validate` passes and `geo` checks pass. Pass 2 is *form and color*. Gate: `geo` + `diag` with no magenta holes and color checks passing. Pass 3, *rig and clips*, runs only if the spec has them. Gate: `validate` behavioral checks pass and the `anim` filmstrip reads correctly. Deterministic failures loop freely for up to **5 build attempts per pass**, because error feedback is what took executability from 70% to 97%. Visual corrections are capped at **3 per pass and 6 in total**. When a cap is hit, Claude stops and shows the user the current sheet with the open Nos. Every review ends in one recorded decision. Edits are local, to the named part, and never a full regeneration, which is how LL3M preserves coherence ([LL3M](https://arxiv.org/html/2508.08228v1)). Before calling any pass done, Claude must show a before/after pair. A pass is never accepted in the same turn the code was first written.

**Evals.** Seed `evals/evals.json` from this game's real needs, and run each eval with and without the skill:

| Eval | Prompt sketch | Scripted assertions (via `inspect`/`validate`) | Judged |
|---|---|---|---|
| Rigid prop + sockets | "Hay wagon, 2.4 m long, hitch socket at front, 4 wheels as separate pivoted nodes" | validate PASS; `Socket_Hitch` exists at z > 0; 4 `wheel_*` nodes with origin at axle height; bbox length 2.4 ± 0.1 | Reads as a wagon (pairwise vs baseline) |
| Node-rigged animal | "Goat with Idle and Walk; legs swing, head bobs" | Clips `Idle`/`Walk` exist; all tracks bind; feet ≥ 0 during the clip; loop seam < 1e-3 | Walk filmstrip shows alternating legs |
| Skinned bend | "Scarecrow whose torso bends in a `Wave` clip, single skinned mesh" | `hasSkins`; 0 validator warnings; weights sum to 1; skinned mesh at root; bbox height never < 80% of bind | No visible collapse at the joint |
| Textured palette | "Crate using a 4-color palette texture" | POT texture; UVs in cell centers; texture is sRGB; renders non-black | Colors match spec |
| Repair | Given `broken.glb` (dotted bone names, pruned socket, weights summing to 0.8, no normals) "fix it" | All four defects reported, then validate PASS | — |
| Edit locality | "Make the wagon's wheels 20% bigger" on a passing asset | Only `wheel_*` nodes changed (inspect diff); other nodes byte-equal | — |

Trigger evals should add about 10 near-miss negatives that must *not* fire the skill: "fix the tractor's physics jitter", "load a Kenney GLB in the scene", "make a 2D sprite". Those belong to `web-3d-game` or nothing.

## Conclusion

The research turns the original question around. "Can Claude see its models?" matters less than "what should Claude not have to see?" Names, weights, normals, bounds, track bindings and loop seams are cheaper and more accurate to measure than to look at. Every image token spent on them is attention taken from the one thing only vision can judge: whether the silhouette, proportions and motion read as the intended object. A skill that gets this split right should have a deterministic validator that is stricter than the Khronos one, and a render tool whose job is to make the remaining visual questions easy, through spacing, labels, auto-framing and before/after pairs.

The biggest unknowns are empirical, and the eval set is the instrument for them. No study has measured Claude specifically as a 3D render critic, compared three.js with bpy as the authoring language, or validated thresholds for foot sliding or silhouette IoU on stylized low-poly assets. The first eval run against the no-skill baseline will show which of these guardrails actually change outcomes. Given VoxelCodeBench's warning that extra context can hurt strong models, anything the baseline already does well should be cut from SKILL.md, not kept.
